Principles

What "trustworthy" means for this repo.

Never touch real data

Every test runs against a throwaway database. A guard aborts the run if the real data/tracker.db is ever targeted.

Evidence, not claims

Coverage, lint and test results are produced by CI on every push and shown as badges and job summaries.

Ratchet, don't regress

Coverage gates start at today's numbers and only move up. A PR can't lower them.

One-command setup

Pinned dependencies, plus pre-commit run --all-files and pytest, reproduce exactly what CI runs.

Roadmap

Phases are ordered so each one makes the next cheaper. Phases 1–3 deliver most of the value.

Test isolation now applies automatically to every test, not only those that request it.

  2. UI tests with Playwright

    Done

    Playwright for Python runs inside the existing pytest suite, with no Node toolchain needed locally. A live_server fixture starts Flask on a random port against the temporary database.

    • Logic tests call page functions directly through page.evaluate(): status ranking and sorting, Rejected/Discarded sinking to the bottom, matchBadge thresholds (49/50, 74/75), pipelinePath backtracking, and HTML escaping in esc() (XSS from scraped job titles).
    • Jobs tab flows: add a job with contacts, change status inline and check it survives a reload, search by contact name, filters synced to the URL and restored from it, column sorting, excluding a company, delete.
    • Other tabs, one or two flows each: practice streak and calendar, recruiter mark-done and reset, system-design and company CRUD, challenge toggles and topic filter, pipeline chart rendering.
    • On failure, save a Playwright trace and screenshot so the cause is visible from CI.

    Done when: roughly 30–40 UI tests pass headless in under 20 seconds.

    Result: 76 UI test cases across tests/e2e/: 35 logic checks, 20 Jobs tab flows, 20 flows covering the other tabs, and 1 test that pins down a known bug. They take about 29 seconds, which is over the 20-second target because there are about twice as many tests as planned. The run was stable across three consecutive passes. The XSS test confirms that scraped HTML in job fields is shown as text and never executed. The tests also found one real bug, listed under Findings.

  3. Frontend coverage

    • Merge results into a per-line report (lcov + terminal summary) next to the Python report.
    • Gate: record the first baseline as the minimum, then ratchet toward 80% lines.

    Done when: CI prints backend and frontend coverage side by side and fails on regression.

    Result: static/app.js is at 99% line coverage (1,263 of 1,276 lines with code). A small pytest plugin, tests/js_coverage.py, records Chromium's coverage data on every test page, maps it to lines (counting in UTF-16 because app.js contains emoji), prints a table next to pytest-cov's, and writes coverage-js.lcov. The gate is --js-cov-fail-under=95. Eight extra tests cover the remaining sort columns and the error alerts, which are triggered by making the browser receive a server error. The 13 lines still uncovered are dead code (see Findings) and two fallback returns that can't be reached.

  5. Linting & formatting

    Done
    ruff check · ruff format

    Python lint and format in one tool. Rules: pyflakes, pycodestyle, isort, bugbear, pyupgrade, bandit (S), simplify.

    biome

    Lints and formats JS and CSS from a single binary. Inline onclick handlers mean "unused function" warnings need an allow-list.

    djlint

    Lints and formats the Jinja template templates/index.html.

    pre-commit

    Runs all of the above on staged files before every commit, using the same versions as CI.

    Done when: the whole repo passes, with the one-off reformat in its own commit so git blame stays useful (listed in .git-blame-ignore-revs).

    Result: pre-commit run --all-files passes. It runs ruff (lint and format), Biome, djlint and the standard file hygiene hooks, and pre-commit installs its own Node, so Biome needs no local Node install. The reformat is a single commit, f4fa0a5, listed in .git-blame-ignore-revs. Changes from the plan, each with its reason recorded in the config:

    • djlint lints the template but doesn't format it. Its formatter would rewrite almost the whole 513-line template just to re-indent it.
    • Biome lints style.css but doesn't format it. The compact one-rule-per-line style is deliberate, and Biome would roughly triple the file's length.
    • Biome's noUnusedVariables is off for app.js. All 15 hits were functions called from inline onclick handlers, and Biome's auto-fix would have renamed them and broken every button.

    Real fixes made along the way: check_job_link_closed now refuses non-http(s) links, because ruff's bandit rule flagged that urlopen also follows file:// (a regression test was added). The other changes are 18 template-literal rewrites, 5 optional chains, Number.isNaN, two forEach callbacks that returned values, and static assets served through url_for. The full suite passes after every change.

  6. Continuous integration

    Awaiting first run

    .github/workflows/ci.yml runs on every push to main and on every pull request, with three parallel jobs:

    • lint: pre-commit run --all-files (ruff, Biome, djlint, file hygiene), then pip-audit.
    • unit: the API tests on Python 3.10, 3.11, 3.12 and 3.13, with the backend coverage gate.
    • full suite with UI tests: every test in headless Chromium with both coverage gates. Coverage tables go to the job summary, coverage.xml and coverage-js.lcov are uploaded, and Playwright traces and screenshots are kept when a test fails.
    • README badges for CI, CodeQL and the license.
    • Branch protection on main: all CI jobs must pass before merging.

    Done when: a red check blocks merging, and badges show live status.

    Status: both workflows pass actionlint, and the exact commands they run pass locally on Python 3.13. CI hasn't run on GitHub yet. Branch protection can only be turned on after the first run, because GitHub needs to have seen the check names.
